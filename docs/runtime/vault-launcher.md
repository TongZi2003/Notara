# Native Vault 的启动与重新打开

在 Native Vault 所在 checkout 中运行：

```sh
npm run vault
```

需要 Node 24 或更新版本。默认数据目录是 `~/.notara/vault-runtime`，默认地址为 `http://127.0.0.1:57093/`。首次运行创建空 Vault；以后保留工作区、课堂、模型配置和浏览器认证签名密钥。关闭终端或 Ctrl+C 只停止服务，不删除数据。

命令会打开默认浏览器并完成 DSH 原生启动令牌交换。如果服务已经运行，复用当前服务并打开其有效入口，不创建另一份数据，也不切换端口。

仅重新打开已运行的课堂：

```sh
npm run vault:open
```

自定义目录或端口：

```sh
npm run vault -- --root /path/to/runtime --port 57093
npm run vault:open -- --root /path/to/runtime
```

`--no-open` 用于后台运行及测试，不操作浏览器。带 token 的当前登录 URL 只保存在数据目录的私有 `launcher.json`；该文件权限为 0600，不应提交或对外分享。未认证的新浏览器访问普通地址仍会收到 401，这是正常的认证边界；应通过 `vault:open` 登录，不需要重填模型 API Key。Cookie 默认有效 30 天，不同浏览器分别持有，固定数据目录和端口下正常重启仍有效。

运行中的数据根由锁保护。端口被占用、目录未登记、登记损坏或保存的启动入口与实际服务不符时，启动失败并保留数据，不删除重建、不改用随机端口。

浏览器 Cookie 按主机保存，不按端口隔离。长期使用同一个浏览器打开不同随机端口的 DSH 实例时，各实例的登录 Cookie 会一起发给 `127.0.0.1`，可能超过 Node 默认 16 KiB 的 HTTP 请求头上限。此时请求在进入鉴权前就以 431 拒绝，内置浏览器可能只显示加载失败；重新发登录链接也无效。Vault 启动器为它启动的 DSH 子进程设置有界的 64 KiB 请求头上限，持久实例与隔离实例一致。签名、HttpOnly、SameSite=Strict、启动 token、Host/Origin 校验均保持原样，不清除其他本机实例的 Cookie。该调整需要重启 DSH 服务生效。

## 意外退出与主动关闭

0.23.9 起，`superviseVault` 每秒核对所属 wrapper 和 Host；确认退出后先清理原 worker，再等待 Host 退出与 `proper-lockfile` 的十秒心跳失效，按原代码、端口和数据目录重新启动。不删除目录锁，不按陈旧 PID 强杀其他进程；鉴权、读取、网络探测不确定时不替换服务。Host 的父 IPC 断开时进入 DSH 自己的关闭流程，避免 wrapper 硬退出留下孤儿服务。

默认十分钟最多恢复三次，退避为一、三、五秒。清理失败、启动失败或超过次数上限会停止自动恢复。运行元数据写入 `launcher-events.log`，不写认证链接、令牌或课堂内容。已保存的课堂与资料保留，进行中的模型回复和后台任务不保证恢复。整个管理进程被结束、电脑关闭或重启不在此恢复机制范围内。

页面左下角红色图标调用 `notaraVault.shutdown`，Host 经同一鉴权私有桥请求 `/shutdown`。受理时同步禁止恢复和新更新，约五百毫秒后停止服务，确保确认回执有机会送达浏览器。桌面控制器委托自己的 `beginShutdown` 清理远控、worker、控制服务和状态/锁；命令行模式停止 supervisor。主动 Stop 也先同步设置停止意图，因此延迟写状态期间不会重新拉起。关闭保留课堂和资料。

## 与测试实例的区别

`startVaultIsolated` 仍使用临时目录、随机端口和合成资料，`stop()` 会清理它自己的临时根。不能将正在使用的课堂长期交给此清理生命周期。`startVaultPersistent` 的回归测试同样使用临时目录，但显式验证停止、重启和迁移后数据仍在。

## 版本更新

0.22.0 起 `vault.ts` 作为启动管理进程，子进程运行 `vault-process.ts` 并持有原来的数据目录锁。Host 经鉴权的私有 loopback 服务访问更新状态；浏览器只调用 `notaraVault.updateStatus/checkUpdate/applyUpdate`，拿不到服务地址、令牌或本机安装路径。课堂与后台任务进行中拒绝重启，更新受理后由原生 `agent/pre-step` 暂停新模型步骤。

管理的启动代码与插件快照必须是同一版本；手动 `git pull` 后若二者不同，需要先 `vault:upgrade`，不让新启动器给旧快照报新版，也保留正确的失败恢复版本。

自动更新读取 `TongZi2003/Notara` 的 GitHub 正式 release，要求 `notara-update.json` 和对应版本 ZIP、SHA-256、DSH/Cordis 版本以及 `docs/runtime/update-contract.json` 中的数据格式标识一致。后台准备成功后才能点击更新。旧服务正常停止后，复用 `vault:upgrade` 换快照，启动新服务成功后才原子登记代码入口；失败重装并启动原代码。启动入口保存在 `notara-release.json`，新代码与本机依赖保存在 `~/.notara/releases/`。不同运行时或数据格式走手动备份升级，不自动迁移。

发布包由 `npm run release:bundle` 生成。推送与插件版本一致的正式标签（例如 `v0.22.0`）会触发 `.github/workflows/release.yml`，检查通过并生成发布包后才创建 GitHub release。只推送普通代码提交不会把它交付给用户；旧用户需先手动升级一次获得检查入口。

发布校验先构建生成资源，再运行测试。失败后可以从 `release.yml` 的手动运行入口指定既有版本标签，重跑该标签代码的完整检查；版本标签和已经公开的 Release 保持不变。

`npm run vault` 在首次创建运行目录时复制一份插件快照；后续启动会保留这份快照与课堂数据。**拉取新代码、重新构建和重新开一个课堂，都不会替换已有运行目录里的插件。** 启动时如果数据目录的版本和代码目录不同，启动器会提示升级。

升级已有运行目录：先停止服务，在代码目录执行

```sh
git pull --ff-only
npm ci --no-audit --no-fund
npm run vault:upgrade
```

自定义目录加 `-- --root /path/to/runtime`。`vault:upgrade` 在服务运行时拒绝执行；它拿到数据目录锁之后：

- 从两处已安装的模块链接识别真实版本，保留旧的带版本号快照；固定位置的 `vault-plugin` 改名留作备份；
- 从当前代码目录复制新的插件快照，依赖链接到这个代码目录（换了新克隆也能用它修好旧链接）；
- 同步切换工作区和 Web profile 的插件链接；同版本更换代码目录也会刷新依赖；
- 将显示默认值放入可修改的 Web profile，已有明确选择保留；home overlay 不再锁住这些设置；
- 按登记的选项重新生成 `home/cordis.patch.yml`，保留已有像素教室；
- 仅迁移下述旧显示种子值，课堂、资料、模型配置和认证材料保留；失败时恢复快照、链接、配置和本次改过的设置。

当前版本显示在“设置 → 学习界面”的最下方，启动日志的第一行也会写出来。完整备份与回退操作见[安装说明](../install.md#升级和回退)，不能只替换插件就假定课堂格式也已回退。

**0.21.0 起 DSH 从 0.1.5-rc.2 升到 0.2.0-rc.1。** 新版 DSH 第一次打开一节课时，把它的记录迁成新格式（旧格式只作为只读存档留在同一目录），旧版 DSH 读不了迁过的课。所以从 0.20.x 升上来之前，先停服务并整份备份数据目录；要退回 0.20.x，需要退回代码目录并执行 `npm ci`，再换回备份的数据目录，只换插件快照不够。0.21 以上的代码目录遇到 0.21 以前的插件快照会拒绝启动，提示先备份、再运行 `npm run vault:upgrade`；升级时旧 `settings.yaml` 里的两处旧种子值（`transcriptView: normal`、更旧的欢迎提示版本）会先改成现在的值，其余设置原样导入。

从旧版 StudyForge 工作台（已退役）切换过来时，按仓库 README 另建代码目录，再首次运行 `npm run vault`。旧版与新版的数据格式不同，不自动迁移 `.trial` 中的卡片、课堂和复习记录。

已在使用 Native Vault、仅想先试本次发布的新版本时，可以另外指定一个空的运行目录和空闲端口：

```sh
npm run vault -- --root ../Notara-Vault-Data-0.21.1 --port 57094
```

这会创建一个独立的新学习空间，不包含原学习数据；保留旧目录，需要时回到原目录启动。代码和运行目录不要整体转发，运行目录中包含本机模型配置与认证材料。升级已有学习空间用上面的 `vault:upgrade`，不要把新建的空空间当成数据升级。

## 迁移已有临时实例

`relocateVaultRuntime(source, destination, port)` 只在原服务停止后调用，目标必须不存在。它复制整个 runtime，原目录改名为 `.pre-persistent` 备份，原路径保留到新位置的目录链接。只调整工作区登记里的内部目录路径，外部资料目录和 session/workspace 身份保持不变；不编辑课堂日志或解析密钥。旧 session header 保存的 cwd 通过目录链接继续解析。持久化启动会检查这些旧路径，缺失时恢复链接，冲突时拒绝覆盖。
