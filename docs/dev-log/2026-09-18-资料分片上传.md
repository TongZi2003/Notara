# 资料分片上传（chunked upload）

## 目标

用户反馈资料上传有大小限制。原链路是「浏览器 arrayBuffer → 整文件 base64 → 单条 remote → Host 全量解码」，`MAX_MATERIAL_BYTES = 64 MB`，且内存峰值约为文件体积 3–4 倍。按「分片上传（真解）」落地：小文件保留单发路径，超过单片大小的文件走 begin/chunk×N/commit 会话，单文件上限同步提到 256 MB。

## 实际改动

### 合同 `packages/contracts/src/material-api.ts`、`material-records.ts`

- 新增 `UploadBeginInput`（operationId/kind:`import|version`/material/expectedVersion?/total）、`UploadTicket`、`UploadChunkInput`（uploadId/offset/base64）、`UploadChunkAck`、`UploadCommitInput`、`UploadAbortInput`。
- `MAX_MATERIAL_BYTES` 64→256 MB，注释说明分片通道承载它：线上不再出现单条巨报文，Host 仍在导入校验前对有界字节数把关。

### Host `packages/host/src/materials/resource-service.ts`

- `PendingUpload` + `pendingUploads` Map（实例态）：kind/material/expectedVersion/operationId/total/received/chunks/expires；TTL 15 分钟惰性清扫，上限 16 个并发暂存（`upload_pending_limit`）。
- `uploadBegin`：先校验 `total ≤ MAX_MATERIAL_BYTES`（`material_too_large`，超大在一个字节暂存前拒绝）与 kind 字段（version 缺 expectedVersion 或 materialId → `upload_version_fields_missing`）。
- `uploadChunk`：偏移必须等于已收字节（`upload_offset_mismatch`），base64 规范校验沿用单发口径（`material_encoding_invalid`），单片 ≤8 MB（`upload_chunk_too_large`），空片与超 total 拒绝（`upload_overrun`）。
- `uploadCommit`：先释放暂存再校验收齐（`upload_incomplete`）——拒绝属于字节不属于会话，不能重复 commit；拼字节后走与单发完全相同的 `MaterialService.import`/`createVersion`，operationId 复用原有幂等语义。
- `uploadAbort`：幂等丢弃，客户端不用记暂存到了哪一步。
- 单发 `import`/`createVersion` 保留：小文件、工具调用与既有测试路径不变。

### 客户端 `packages/client/src/materials/material-upload.ts`（新）

- `uploadMaterialFile`：`file.size ≤ UPLOAD_CHUNK_BYTES(4 MB)` 走原单发 remote；否则 `file.slice` 逐片读盘→base64→`uploadBegin/chunk/commit`，任一步失败 best-effort `uploadAbort` 后把 remote 拒绝原样抛出（调用方照旧按错误码匹配）。
- `onProgress` 回调回报已收字节数。

### `MaterialsPage.tsx`、`lesson-uploads.ts`、`files.ts`

- `Unsettled` 从缓存「整包 base64 载荷」改为缓存上传请求（file+operationId+material），重试按同一 operationId 重跑——语义不变：同一上传不会变成第二份。
- `send` 改用 `uploadMaterialFile`；分片进行中 notice 显示「正在收下… NN%」。
- `MaterialsFace` 删掉无人再调的 `importMaterial`/`createVersion` 成员与 `register-materials.tsx` 对应实现。
- `lesson-uploads.ts`：`row.upload`（缓存 base64）删掉，`uploadMaterialFile` 复用 `row.id` 作 operationId，进度写 `row.message`。
- `files.ts` 的 `material_too_large` 文案改为从 `MAX_MATERIAL_BYTES` 常量插值，不再硬编码 64。

### 测试

- `tests/integration/material-chunk-upload.test.ts`：9 MB 三分片导入+字节回读全等+同 operationId 重跑仍是同一份；分片版追加落第二版；begin 超大/缺 version 字段、乱序偏移、overrun、非法 base64、未收齐 commit、过期/未知 uploadId、abort 幂等——全部断言真实错误码。
- `tests/e2e/material-upload.spec.ts`：9 MB md 走 UI，`page.route` 给 uploadChunk 加 400ms 延迟使进度提示确定性可见，断言「正在收下」→「收好了」→行出现→rpc 字节回读全等→打开能读→控制台零异常。
- `tests/fixtures/http-runtime.ts`：rpc/login fetch 加 `connection: close`——本轮抓到真实的 undici 竞态：服务器已决定关闭的 keep-alive 池化连接上分派 POST 不重试，测试报 `ECONNRESET`；每请求独立 socket 消掉整类竞态。

## 过程中抓到的真问题

- e2e 第一轮 `material_content_invalid`：fixture 按字节数截断最后一行，截在多字节字符中间产生非法 UTF-8——校验诚实拒绝了坏文件，修 fixture 只写整行、尾部补换行。
- 「更新原文」文件上传 UI 已是死代码：`MaterialRow`/`addVersion` 不被任何 JSX 渲染（shelf 换成 `LibraryBrowser` 后失去挂载点）。本轮已把 `addVersion` 迁到新协议保持一致，但 UI 没有文件版入口是既有事实，记入待办。
